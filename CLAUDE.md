# CLAUDE.md — fair-football-fee

Claude is the lead developer on this project (owner: Gunnar, `gunnarwrld/fair-football-fee`). This file is the working contract for every session. The full decision history and its reasons are in `docs/PROJECT_LOG.md`; read it before changing anything in the data or ML layers.

## What this is
A portfolio regression system that estimates a Premier League player's **Transfermarkt crowd-sourced market value** (not an actual transfer fee) at a date `t`, using only data dated strictly before `t`. XGBoost model → FastAPI service with Redis cache-aside → Next.js UI. The owner is a backend-focused full-stack student and needs to be able to defend every design choice.

## Hard invariants (do not break without updating PROJECT_LOG.md)
1. **Point-in-time:** every feature uses source rows dated `< as_of_date`. Ongoing injuries are clipped at `t`. `tests/test_leakage.py` (truncation invariance and train/serve parity) must stay green.
2. **Modeling population (Phase 2.1):** train, evaluate and serve only rows with `in_model_population == True`: `GB1`, ≥ 450 tracked minutes in the prior 365 days, and a club confirmed by match data. Liga Pro Ecuador is out of scope. See `docs/phase2_1_population_findings.md`.
3. **Target:** `target_log_ratio_vs_league_median = ln((y+1)/(M+1))`, where `M` is the trailing-365-day league median **over the same population**. Predictions are un-normalized with the same `M`. SHAP values are log-space and are shown as multiplicative `exp(phi)-1` "vs league median".
4. **Main model has no contract feature and no lagged value.** `VALUE_UPDATE_MODEL_FEATURES` (lagged value; baseline = carry the last value forward) and `CONTRACT_ABLATION_FEATURES` (tiny recent window) are secondary experiments only.
5. **Splits** (`src/features/engineer.py`, whole July–June cycles): train < 2023-07-01 ≤ val_tune < 2024-07-01 ≤ val_calib < 2025-07-01 ≤ test. Tune on val_tune; conformal calibration on val_calib; touch test once per model version.
6. **Feature and model decisions come from train-only CV or val_tune, never from test.** If a test number tempts you, write it in PROJECT_LOG and still decide by CV (Phase 3 precedent: season-phase feature).
7. **Alembic is the only schema source.** No raw SQL schema files. `alembic check` must report no drift.
8. **`data_version`** comes from `data/raw/MANIFEST.json` (written by ingestion) and is never hardcoded. The active model comes from `model_versions.is_active`, not config.
9. **salimt data has no license:** never commit its raw or derived parquet, and never expose raw injury records through the API.
10. No synthetic data attached to real players. Test fixtures use obviously fake players.
11. **Served estimate = model output + recentering offset (Phase 4).** The offset and the interval quantiles come from `artifacts/<v>/conformal.json` (= `model_versions.conformal_quantiles`), calibrated on val_calib only. The offset uses only out-of-sample update batches that ended before the prediction's own batch began. After any data refresh or retrain: `make calibrate` → `make register`.
12. **Redis is an optimization, never a dependency (Phase 5).** Any Redis failure degrades to `X-Cache: BYPASS` (the rate limiter fails open), never to an error. Cache keys always include `model_version` and `data_version`.
13. **What-if goes only through `src/features/whatif.py`:** the five inputs in `WHATIF_BOUNDS` (the training range), with every dependent feature recomputed by the pipeline's formulas. Injury inputs are never offered (they explain low minutes, Phase 4).
14. **A change to an API response shape bumps `RESPONSE_SCHEMA`** in `src/api/service.py` (part of every cache key, so a deploy never parses JSON cached by the previous version) **and regenerates `frontend/src/lib/api-types.ts`** (`npm --prefix frontend run api:types` with the API running).

## Commands (see `Makefile`)
- `make pipeline` ingest → clean → features · `make train` Phase 3 (reuses `tuning.json`) · `make train-retune` · `make calibrate` Phase 4 · `make register` (needs `make db`) · `make api` (FastAPI on :8000, docs at `/docs`; needs `make db` + `make register`) · `make web` (UI on :3000; needs `make api`) · `make web-check` (frontend type-check, lint, vitest, build) · `make report` · `make test` / `make test-unit` · `make lint`
- After `make train` or a data refresh, always run `make calibrate` then `make register`: the model, intervals and offset must come from the same run.
- Remote VM: SQLite can't run on the mounted repo (no delete permission for journals), so pass `--optuna-db ~/optuna_v1.db --tune-timeout 150` and rerun until tuning completes.
- `make db` = docker postgres+redis → `alembic upgrade head` → load clean tables → load serving features. Host Postgres port is **5433** (5432 is taken on the owner's Mac by a native Postgres).
- Tests marked `@pytest.mark.data` need the local lakehouse and skip on a clean clone. Tests marked `@pytest.mark.db` need the local Postgres, run inside a rolled-back transaction, and skip when it's unreachable. `make test-unit` excludes both.

- Phase 3 facts to carry forward (details in `reports/phase3_evaluation.md`): XGBoost and Ridge are statistically tied; XGBoost ships for TreeSHAP and missing-value handling. The contract feature shows no detectable signal, so contract length is read-only in the UI. The value-update model beats carry-forward.
- Phase 4 facts to carry forward (details in `reports/phase4_explain_intervals.md`): the served estimate adds the recentering offset (invariant 11), which removes most of the out-of-time bias. Intervals: 80% displayed, 90% stored, one quantile per quartile of the model's predicted ratio (bin edges in `conformal.json`); interval = `expm1(pred_ratio + offset ± q[level][bin] + ln(1 + M))`. SHAP comes from `explain.shap_contributions` (XGBoost `pred_contribs`), age + age² grouped, labels in `explain.DRIVER_LABELS`; show the offset as its own driver. More injury days *raise* the estimate (they explain low minutes), so in what-if mode injury days must move with minutes or stay read-only.
- Phase 5 facts to carry forward (contract in `/docs`, reasons in PROJECT_LOG): player ids are internal `players.id`, returned by `GET /v1/players?q=` together with `has_valuation`. A valuation carries the estimate, the 80% `interval` plus all `intervals`, `market_value` (the Transfermarkt value on `as_of_date`, to compare with), `baseline_eur`, the top 5 `drivers`, `other_drivers_effect_pct` and the `adjustment` (recentering) line, which multiply back exactly: `(1 + baseline) · Π(1 + effect) · (1 + other) · (1 + adjustment) = 1 + estimate`. `POST /v1/valuations` takes `{player_id, scenario}` and adds `changes`, `current_estimate_eur`, `change_pct`. Errors are `{"detail": {"code", "message"}}`. The what-if rate limit is per client IP, so the frontend must call the API from the browser, not from Next.js server code (all users would share one bucket). CORS allows `http://localhost:3000`.
- Phase 6 facts to carry forward (details in `frontend/README.md` and PROJECT_LOG): all data is fetched in the browser with SWR. Slider ranges and every metric on the About page come from the API, never from frontend literals. Chart colors are the dataviz palette, validated for both modes; re-run its validator if they change. Money goes through `formatEur`, never `Intl` compact notation (it differs by runtime).
