# Project Log: Decisions and Why

A running record of design decisions, review findings and rejected alternatives, newest at the bottom. Each entry gives the reason in plain language so it can be defended. `CLAUDE.md` holds the current rules; this file explains how they came about.

## Origin (2026-10-26)
Brief: estimate fair market value from historical stats, injuries and contract length (Premier League and/or Liga Pro Ecuador), with XGBoost served through a REST API with Redis caching.

## Phase 0: Architecture
- **Target = Transfermarkt market value, not transfer fees.** It's the only open, consistent target. Fees depend on release clauses, add-ons and leverage. Disclosed in the README and model card.
- **FastAPI over Express + ONNX.** ONNX graphs export predictions only, not TreeSHAP attributions. Serving in Python also shares the exact feature code with training, so there is no train/serve skew. Rejected: Node + ONNX (permutation SHAP would be slow, and the features would have to be re-implemented in TypeScript).
- **Parquet lakehouse + 6 Postgres serving tables.** Raw, clean and features live as Parquet (fast, reproducible). Postgres holds only what the API serves. Rejected: a 4-schema, 15-table Postgres ETL (too much boilerplate for a portfolio project).
- **`player_current_features` table.** The API reads one precomputed feature row and applies what-if overrides on top, so nothing is recomputed per request.
- **Alembic is the only schema source.** A hand-written SQL file alongside it would drift. `alembic check` is part of verification.
- **`player_seasons` unique key** `(player_id, season, tm_club_id)`, because mid-season transfers within the same league would collide on a league-based key.
- **Ports bound to 127.0.0.1**, a partial unique index guarantees a single active model, and `data_version` comes from the ingestion manifest rather than config.
- **Main model is contract-free.** The only contract-expiry fields are current snapshots, so using them for historical valuations leaks later renewals, and renewals correlate with quality.
- **FBref advanced stats unavailable.** Opta terminated FBref's feed in early 2026 and the xG/progressive metrics were removed, so the core features use Transfermarkt-derived data only.

## Phase 1: Audit, ingestion, cleaning
- **Sources:** dcaribou/transfermarkt-datasets (CC0; valuations, appearances, games, transfers) and salimt/football-datasets (no license; injuries and profiles). Both are pinned by SHA-256 and commit SHA, and their hashes are recorded in `MANIFEST.json`.
- **Point-in-time league attribution** comes from games per club-season, because the clubs table stores a club's *current* league. Promotion and relegation would otherwise leak. This fix caught 8,332 mislabeled "GB1" rows.
- **Contract validity check:** the per-row test uses salimt's own snapshot consistently. Mixing two snapshots (dcaribou expiry from June 2026 with salimt extensions from Sept 2025) hid renewals. Only about 1,600 rows are valid, almost none in test, so the contract ablation is expected to be inconclusive. Show contract length in the UI as read-only; don't promise a slider.
- **EC1 identified as a survivorship sample:** Ecuador-stage valuations of players who later reached tracked clubs.

## Phase 2: Point-in-time features
- One feature code path (`engineer_features_for_snapshots`) serves both training snapshots and serving rows.
- Empirical-Bayes per-90 shrinkage (m0 = 900 minutes) with priors fitted on train only. Injuries are clipped at `t`. A lagged value is used only by the value-update model.
- Tests: synthetic edge cases at `== t` / `> t`; truncation invariance on real snapshots (delete everything dated ≥ t, recompute, require bit-for-bit equality); train/serve parity.
- Target normalized by the trailing league median, because trees can't extrapolate a year or level trend into the test period.

## Phase 2.1: Era-stable population (2026-10-29)
Review of the Phase 2 data found that the dataset's population changes right at the train/val boundary. Full evidence is in `docs/phase2_1_population_findings.md`. In short:
- Older seasons contain fringe players who are in the source only because they appear later; recent seasons haven't had time to collect them. The median value jumped from €7M to €15M in one season while the same players' values were flat, so the old league index tracked population changes, not inflation (val_tune +0.13 vs test −0.28 mean log ratio).
- **Decision:** GB1 rows with ≥ 450 tracked minutes in the prior 365 days, plus club attribution confirmed by match data. The league index is computed on that population. Era-dependent features are replaced (appearance-based tenure capped at 730 days, capped injury recency, injury features NULL outside the injury source). Constant columns are no longer features.
- **Liga Pro Ecuador dropped** (owner's decision): 27% of rows have season stats, under 1% have match data, about 180 rows would survive the population rule, single digits in test.
- Result: a smooth index from €4.8M (2013) to €23.5M (test); mean log ratio between −0.07 and −0.13 across val/test; null-rate gap train vs test ≤ 1.5 points for every feature. Population: train 8,401 / val_tune 1,118 / val_calib 1,101 / test 1,288. Serving: 439 players.
- Follow-up: derive club-at-valuation from appearances in Phase 1 instead of excluding unverified rows.

## Phase 3: Baselines, XGBoost, evaluation (2026-10-29)
- **Protocol:** Stage A fits every model on train and compares on val_tune. Stage B refits on train + val_tune and scores test once. val_calib is reserved for Phase 4. Optuna (80 trials) uses expanding-window folds inside train only. Results: `reports/phase3_evaluation.md`, generated entirely from `artifacts/v1.0.0/metrics.json`.
- **Model choice:** tuned XGBoost and Ridge are statistically tied (player-level block bootstrap CIs include 0 on val_tune and test). XGBoost ships for native missing values, interactions and exact TreeSHAP; Ridge stays as the interpretable reference. Saying "tied" honestly is stronger in a defense than claiming a win that isn't significant.
- **Bug found and fixed:** the value-update model used `prev_log_market_value` (absolute) against a ratio target. Trees can't extrapolate, so in an inflated season ordinary players' previous values looked like past stars', giving a worse model than carry-forward. Replaced with `prev_log_ratio_vs_league_median` (same scale as the target); it now beats carry-forward with a CI clear of zero.
- **Out-of-time bias:** predictions run systematically high on later seasons, and the shift differs per Transfermarkt update batch (a trailing median lags market-wide corrections). Two point-in-time candidates (`days_into_season`, `index_growth_365d`) were **rejected by train-only CV**. The test split looked better with the season-phase feature; it was still rejected, because choosing on test would be snooping. Both comparisons are recomputed by `train.py` for the record. Carried to Phase 4: recentering by the latest batch residual, and per-batch conformal coverage.
- **Contract ablation:** with/without difference is inside its CI on the ~200 test rows with a valid contract, so contract length is read-only in the UI.
- **Ops:** XGBoost CPU wheel (`xgboost-cpu`) in the Linux VM to avoid a 291 MB GPU dependency. Optuna storage is SQLite with resume support (`--optuna-db`, `--tune-timeout`). `make train` reuses the committed `tuning.json` so results are reproducible.

## Phase 4: Explanations, intervals, recentering (2026-10-29)
Results: `reports/phase4_explain_intervals.md` and `reports/model_card_v1.0.0.md`, generated from `artifacts/v1.0.0/phase4_metrics.json` and `conformal.json` by `make calibrate`.
- **Decision protocol.** Recentering and the interval method were chosen on a rolling backtest that repeats the final layout one season earlier at a time: fit on every cycle before E−1, calibrate on E−1, evaluate on E, for E = 2019/20 … 2023/24. It reads only train and val_tune. val_tune alone has four update rounds, too few to judge a correction shared by every row in a round; the backtest has 30 batches. Both rules are written in `src/ml/calibrate.py` and were fixed before any result was seen. Test was scored once, after the decision.
- **Recentering adopted.** Transfermarkt updates the league in rounds; a batch is a run of valuation dates with no gap over 14 days. Each prediction is shifted by the median out-of-sample residual of the latest batch (≥ 50 rows) that ended before the prediction's own batch began, so it reads only valuations published before the prediction. Backtest MdAPE 34.8% → 32.7% (−2.1 pts, 95% CI −4.6 to −0.2, resampling whole batches). On test: MdAPE 33.4% → 26.6%, mean log bias −0.218 → −0.062. Every player in a round moves by the same factor, so rankings and SHAP drivers don't change.
- **Intervals: split-conformal, one quantile per predicted-value quartile (Mondrian).** Score = |log residual| after recentering, calibrated on val_calib only. With one global quantile, the worst predicted-value bin was 12.8 pts off nominal coverage in the backtest; per-bin quantiles cut that to 2.8. The bins use the model's own prediction because the actual value isn't known when the interval is made.
- **80% is the displayed level** (typical width ×/÷ 1.61 on test); 90% is stored too (×/÷ 1.94) but is too wide to be the headline. Product choice, not tuned on any split.
- **Test, scored once:** 80% coverage 77.0% (95% CI 73.7–80.1, player-block bootstrap), 90% coverage 88.1% (85.6–90.3). Weakest cells: goalkeepers and players whose actual value ended under €5M. All four configurations were also scored on test for the record; the chosen one also has the smallest worst-bin gap there, so no test number argued against the decision.
- **TreeSHAP via XGBoost's `pred_contribs`.** Exact, identical to `shap.TreeExplainer` on a 200-row check, handles the categorical splits, and keeps a second explainer library out of the API image. Values are log-ratio units shown as `exp(phi) − 1`; age and age² are summed into one driver, and the recentering offset is its own line ("latest update-round adjustment"). Readable names live in `explain.DRIVER_LABELS`.
- **Finding for the what-if UI:** more injury days *raise* the estimate. Long-injured players have fewer minutes, and the injury feature tells the model why: low minutes without an injury usually means a squad player. Checked with a one-off SHAP-by-bucket breakdown on test. Injury days therefore can't be a free-standing what-if slider; they must move together with minutes, or stay read-only.
- **Serving config:** `artifacts/v1.0.0/conformal.json` is stored as `model_versions.conformal_quantiles`. All 439 serving players reproduce their test row on the same date (same prediction, same offset). The offset depends on the data, so `make calibrate` must run after every data refresh, and `make register` refuses a stale offset. v1.0.0 is registered and active.
- **Small changes:** `metrics.block_bootstrap_ci` shares the resampler with `block_bootstrap_diff` (same random sequence, same Phase 3 numbers). `models._load_native` is now public `load_native`. Ruff 0.17 flags unparenthesized implicit string concatenation in lists (ISC004), so long report strings are wrapped in parentheses. New pytest marker `db` for tests that need the local Postgres; `make test-unit` excludes `data` and `db`.

## Phase 5: FastAPI + Redis (2026-10-29)
- **Endpoints as planned in Phase 0:** `GET /v1/health`, `GET /v1/model`, `GET /v1/players?q=`, `GET /v1/players/{id}/valuation`, `POST /v1/valuations` (what-if). Errors are `{"detail": {"code", "message"}}`; every response carries `X-Request-ID`, valuations also `X-Cache`. OpenAPI docs at `/docs`.
- **Plain `def` routes.** SQLAlchemy, redis-py and XGBoost are all blocking, so FastAPI runs the routes in its threadpool. `async def` would either block the event loop or need async drivers for all three, for no gain at this scale. XGBoost is pinned to one thread per prediction so parallel requests don't oversubscribe the CPU.
- **Layers:** routes (HTTP only) → `service.py` (use cases, domain errors) → `repository.py` (all SQL) and `src/ml/predictor.py` (estimate, intervals, SHAP). Components live on `app.state` and are passed to `create_app`, so tests inject fakeredis, a fake runtime and an in-memory repository instead of patching modules.
- **What the API serves is read from the database, never config:** the active model from `model_versions` and the data version from `player_current_features`, re-read every 60 s. Valuations return 503 when the calibration's data version differs from the serving data, when the serving table holds more than one data version, or when the artifact can't be loaded. Wrong-but-plausible numbers are worse than an honest 503.
- **Parity:** the API reproduces the offline Phase 4 estimate exactly (relative difference 0.0 on the worked example); a `db` test keeps it that way.
- **Cache-aside** with Phase 0's keys `valuation:{model_version}:{data_version}:{player_id}` and `…:whatif:{sha256(payload)}`, so a model or data switch can never read an old entry. A singleflight lock (`SET NX EX 5` holding a random token) lets one request compute while the others poll for its result; the lock is released with a `WATCH`/`MULTI` compare-and-delete, so a request never deletes a lock someone else now holds (no Lua: fakeredis can't run it without `lupa`, and `WATCH` is just as atomic). Redis is optional: 0.25 s socket timeouts, and after an error a circuit breaker skips Redis for 30 s, so a dead Redis costs one timeout per window and requests are answered uncached (`X-Cache: BYPASS`).
- **Rate limit:** 60 requests per minute per client IP, on `POST /v1/valuations` only, the one path where a client can force uncached model work. GETs are bounded by the 439 cacheable players. Fixed window in Redis, fail-open. `X-Forwarded-For` is ignored because any client can forge it; behind a proxy this needs a trusted-proxy setting.
- **What-if design (`src/features/whatif.py`):** five inputs (age, minutes, appearances, goals, assists in the last 12 months). An input you set is taken as given; a count you don't set keeps its per-minute rate, so "more minutes" means the same player playing more. Every dependent feature (24-month windows, minutes trend, shrunk per-90 rates) is recomputed with the pipeline's own formulas. The position prior is read back from the stored rate, so serving needs no prior file, and a data test checks the math on all 439 serving rows. Inputs are limited to the training range, and impossible combinations are refused with a 422 that says why. Injury inputs aren't offered (Phase 4 finding).
- **Bug found and fixed:** a player outside the injury source has JSON `null` injury features. A one-row DataFrame built from them gets object-typed columns, and XGBoost rejected them, so that player got a 500. One current player was affected. `feature_frame` now converts object-typed numeric columns to numbers with NaN (training data is already numeric, so Phase 3/4 results are unchanged); there are regression tests at unit and `db` level.
- **`predictions_log`:** one row per valuation, written by a background task with its own session after the response is sent; a failed audit write is logged, never turned into an error.
- **Measured** (dev server, one sequential client): cached valuation p50 2.4 ms, uncached what-if p50 16.4 ms, name search p50 10.1 ms. Real load testing (k6) is Phase 7.
- **Deferred to Phase 7:** `Dockerfile.api` (the compose `app` profile already references it) and a trusted-proxy setting for the rate limiter.

## Phase 6: Next.js frontend (2026-10-29)
- **Stack:** Next.js 16.4 (App Router, Turbopack, Cache Components as scaffolded), React 19.3, Tailwind 4, TypeScript, SWR, vitest; current stable versions checked on npm that day. The scaffold's Google font was replaced by the system sans, so the build needs no network (Phase 7 Docker) and the dataviz guidance's typeface rule holds. `@types/node` moved to ^24 because vitest 5 needs ≥ 22 (no `--force`).
- **The browser calls the API directly**, because Phase 5's rate limit is per client IP. Pages are static shells. The player page reads its route param inside `<Suspense>`, as Cache Components requires, and the production build confirms it: `/` and `/about` are static and `/players/[id]` is a partial prerender. SWR deduplicates the model-info request shared by the footer, the about page and the what-if bounds, keeps the previous result while refetching (no skeleton flash), and doesn't retry 4xx answers.
- **Types are generated from the API's OpenAPI schema** (`openapi-typescript`, `npm run api:types`), so a backend change that breaks the UI fails the type-check instead of the browser.
- **API additions for the UI:**
  - `inputs`: the five what-if inputs behind a valuation, so the sliders start at the player's values.
  - `context`: injury totals and contract end, shown read-only.
  - On `GET /v1/model`: `whatif_bounds`, so the UI and the API share one range definition, and `point_without_recentering`.
  - Because the response shape changed, cache keys gained a schema version (`valuation:s2:…`), so a deploy never parses JSON cached by the previous version.
- **Honest-comparison fix:** the first About page compared the served error (with recentering) to Ridge without it. Most of that gap is the adjustment, which would apply to any model, so the page now shows the served error next to the same model without the adjustment.
- **Charts follow the dataviz guidance:**
  - The palette was validated with its script in both modes. Driver bars use a diverging blue/red pair (CVD ΔE 21.6 light, 19.2 dark); the interval uses a three-step one-hue ramp.
  - Driver bars are on a log scale (a doubling and a halving have the same length) and sit inside a table, so the chart is its own table view.
  - The interval chart uses a legend that carries the numbers instead of colliding direct labels.
  - Hover and keyboard-focus tooltips.
- **Bug caught in the browser:** `Intl` compact currency formatting differs between runtimes (Node prints "€22.4M", Chrome "€22.4m"). It was replaced by a small deterministic formatter, unit-tested including rounding across units (€999,960 is "€1M").
- **Verified in the browser against the live API:** search, player page, a what-if result and the 422 explanation for an impossible scenario, the about page, dark and light mode, and 375 px width (the driver table moves values under labels on phones).
- **Tests:** 13 frontend unit tests (formatters, axis ticks, and the identity the UI relies on: baseline × every driver's factor = estimate), plus API tests for the new fields.
- **Deferred to Phase 7:** the frontend Dockerfile and the compose `app` profile (`NEXT_PUBLIC_API_BASE_URL` is baked in at build time, so it becomes a build argument), and CI running `make web-check`.
