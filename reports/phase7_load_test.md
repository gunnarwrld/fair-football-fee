# Phase 7: load test

Generated by `make loadtest` (`scripts/loadtest.sh` → `loadtest/api.js` → `scripts/loadtest_report.py`) on 2026-10-30, code at `99eacbe-dirty`. The numbers depend on the machine and on what else it is running, and vary between runs on a shared laptop (the project log lists the range seen): rerun to compare.

## Setup

- **API:** the `Dockerfile.api` image with 2 uvicorn workers. Each worker takes at most 16 requests at once (more get an immediate 503 "busy") and has 15 database connections, waited for at most 2 s.
- **Machine:** Docker Desktop with 10 CPUs and 7.7 GiB, shared by the API, Postgres, Redis, k6 and any other running container.
- **Load:** `grafana/k6:2.2.0` on the same Docker network. It uses an open model (fixed arrival rates), so a slow API faces a growing backlog, as it would with real users. 276 players were found through the search endpoint and their valuations cached in `setup()`. Valuations then come from Redis when it is up, search is never cached, and every what-if is a new scenario, so always a cache miss (model + TreeSHAP). The three request types run at the same time for 60 s per run. The per-IP what-if limit is lifted, because k6 is a single client.

## What the numbers say

- **With Redis**, cached valuations were served at a p95 of 48.0 ms (100.0% cache hits). What-ifs, which always run the model and TreeSHAP, took 207.9 ms at p95.
- **With Redis stopped at the same load**, every valuation had to be computed. The API served 78 of the 260 requests per second and refused the rest at once with 503 "busy". 0 responses were errors, and 99% of all responses came back within 986.9 ms.
- **With Redis stopped at a quarter of the load**, 100.0% of valuations were served and nothing was refused: every valuation was computed, at a p95 of 49.0 ms.
